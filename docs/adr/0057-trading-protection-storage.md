# ADR 0057：三项交易保护各用独立存储键

- 状态：已在工作树实施（2026-11-19），未合入 `main`、未发布。
- 关联：[运行时规则 §12](../runtime-guardrails.md#12-trading-protection-preferences)；[ADR 0045](0045-l1-action-expiry.md) 决策 6（延迟保护）；[确认面](../confirmation-surfaces.md)；[第二波修复记录](../work-memory/sessions/2026-11-12-second-wave-fixes.md)的「已知边界」；[任务记录](../work-memory/sessions/2026-11-19-trading-protection-storage.md)。

## 背景

下单确认（`skipOrderConfirmation`）、市价单最大滑点（`marketOrderSlippagePercent`）和延迟保护（`transactionDelayProtection`）原来和主题、数字格式等普通设置一起存在 `global-settings-v2` 这一条记录里（版本 4）。2026-11-19 的审查（`r2-wave2-signing` P1-1、P2-2、P2-3）在本地 jsdom 测试里复现了三种静默放宽：

1. 仍在运行旧版本的标签页改任何设置时写回整条记录，新标签页实时应用或冷启动读到它，三项保护回到旧值；缺滑点字段的旧记录让已收紧的滑点回到默认 `2.5%`。
2. 两个当前版本的标签页：A 读出记录、B 在 A 写入前收紧确认、A 再按旧快照合并写回，B 的收紧丢失。
3. 版本高于 4 的记录：冷启动经 zustand `migrate` 应用其中的宽松值，并以版本 4 写回；当前页改主题也会整条覆盖它。

## 目标与约束

- 三项保护只能被本窗口里用户的显式操作放宽。来自存储事件、往返缓存恢复、冷启动或其他设置合并的值，按下面的明确规则决定是否采用。
- 旧版本代码读到新格式不崩溃、不放宽；新版本读到旧格式能迁移；回滚发布后的行为可预期。
- 不改变其他设置的同步行为（第二波修复的「只写自己改的字段、其他窗口实时跟随」保留）。

## 依据（外部行为）

- WHATWG HTML《Web storage》：`storage` 事件只发给持有同一存储的**其他**窗口，发起修改的窗口收不到；`setItem` 对单个键是一次赋值，写完才广播；规范明确让作者「assume that there is no locking mechanism」，即跨标签页没有事务。MDN《Window: storage event》同样说明事件不在发起修改的窗口触发。
- W3C《Web Locks API》：锁管理器按存储桶共享，`request()` 只排斥同样申请这把锁的代码，接口只在安全上下文提供。旧版本代码不会申请锁，同步的 `localStorage` 读改写也不在锁内，所以 Web Locks 不能解决旧标签页的整条写回。
- zustand 5.0.9 `persist`（`node_modules/zustand/middleware.js`）：创建 store 时同步调用存储的 `getItem` 并 `merge`；记录版本不等于 `version` 且提供了 `migrate` 时，迁移后立即 `setItem` 写回——这就是高版本记录被降级写回的路径。

## 决策

1. **存储格式。** 每项保护一个键，值是 JSON：`skip-order-confirmation-v1`（布尔）、`transaction-delay-protection-v1`（布尔）、`market-order-slippage-v1`（数字，读取时按 0.1%–5% 夹紧）。这些键只由该项保护的显式设置操作写入，一次 `setItem` 写一个值，没有读改写。另有迁移基线 `trading-protection-baseline-v1`（三项的 JSON 对象）。
2. **迁移只做一次。** 冷启动时没有基线、且 `global-settings-v2` 不是更高版本，就按旧版本的读法（缺字段或类型不对用默认值）从这条记录写出基线；已有基线则不再写。读取每项时：自己的键优先；键存在但读不出时取最严格值（开确认、开延迟保护、`0.1%`）；没有自己的键时用基线（基线读不出也取最严格值）；都没有用默认值。两个窗口同时初始化只可能互相覆盖基线，基线从不覆盖显式写入的键。迁移之后，新版本不再从 `global-settings-v2` 读这三项。
3. **哪些值被采用。**
   - 冷启动：采用上面读出的值，即每项最后一次被提交到存储的显式选择（其他窗口的放宽也在下次打开时生效）。
   - 已打开的窗口（存储事件，键为设置记录或三个保护键之一；往返缓存恢复；本窗口写普通设置之后）：每项取「本窗口当前值」与「存储读出值」中更严格的一个，只收紧、不放宽。
   - 本窗口的显式操作：可以放宽，先写自己的键，再更新内存。
   - 同一项在两个窗口几乎同时被显式修改时，以最后完成的 `setItem` 为准；不同项互不影响。不需要修改序号或时间戳（墙钟本身不可靠，且每个键只有显式操作这一个写入来源），也不需要 Web Locks。
4. **给旧版本看的回滚值。** `global-settings-v2` 继续保持版本 4，普通设置照旧在里面读改写。新版本每次写这条记录时，三项保护写成「记录里原有值（缺省按默认）」与「新版本读出值」中更严格的一个；冷启动时若记录里的值比这个更宽松也补写一次。因此回滚发布或仍在运行的旧标签页读到的值，既不比它自己上次存的宽松，也不比新版本的最新选择宽松。代价：新版本里的放宽不会传给旧版本，回滚后用户可能看到比自己最新选择更严格的保护。
5. **更高版本的记录。** 版本号在校验正文之前、用同一次读取判断。高于 4 时：不迁移、不清理、不写入（普通设置和投影都不写），记录原样保留；冷启动仍从正文里读能通过本版本校验的普通设置（与此前冷启动一致，主题首屏脚本无需改动），三项保护从独立键读，不从这条记录读；本窗口的普通设置修改只留在内存。三项保护的显式修改仍写自己的键。
6. **版本号。** 低于 4 的记录仍像以前一样在冷启动迁移后按版本 4 写回（三项保护按决策 4 写）。本次不提升 `global-settings-v2` 的版本号，回滚后的旧代码无需迁移即可读取。以后若提升，旧代码对高版本的处理以那一版的代码为准；本版本按决策 5 处理。

## 备选方案

| 方案 | 取舍 |
| --- | --- |
| 整条记录加 Web Lock | 旧代码不参与；同步读写不在锁内；锁只在安全上下文提供。不能解决 P1-1。未采用 |
| 整条记录加时间戳或修改序号 | 旧代码写回时会丢掉未知字段，新代码无法判断记录里的保护值是新是旧；普通设置的写入仍会带出过期的保护值。未采用 |
| 每项一个键，再加修改序号 | 每个键只有显式操作一个写入来源，最后完成的写入即最新；序号不增加信息。未采用 |
| 给旧版本的记录固定写最严格值（草稿方案） | 实现更简单，但仍在运行的旧标签页一收到事件就被改成 `0.1%` 滑点，回滚后所有用户也都是 `0.1%`。改为决策 4 的「取更严格者」 |
| 迁移后仍从旧记录接受「更严格」的值 | 回滚期间在旧版本里收紧的值能带回来；但新版本写给旧版本的值本身就是更严格者，新版本里的显式放宽会被永远压回去。未采用 |

## 后果与边界

- 迁移之后，在旧版本里（旧标签页或回滚期间）对这三项的修改不会带回新版本；重新升级后，各项回到在新版本里最后一次的显式选择。若那次选择比旧版本里的修改宽松，这就是一次不是由当前窗口显式操作造成的放宽。只在「升级—回滚—在旧版本里收紧—再升级」时出现。
- 首次迁移读取的是当时的旧记录；它若已被旧标签页写成过期的宽松值，无法识别。
- 一个窗口内的放宽不会传给已打开的其他窗口，这些窗口的设置面板继续显示更严格的值，直到刷新或在本窗口改动。
- 普通设置和投影仍是读改写，`localStorage` 没有跨标签页事务，在同一任务的读和写之间落下的其他窗口写入仍可能被覆盖（包括恰好在此刻写入的更高版本记录）；三项保护的键不受影响。
- 浏览器存储不可用（禁用、配额满）时，设置只在本窗口内存生效；显式写入失败时，下一次读取存储只会让它变严格。
- 真实浏览器多窗口、真实的发布回滚未验证；验证范围见任务记录。
